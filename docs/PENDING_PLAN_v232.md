- risks:
  1. **Dual-copy hazard** (v182 / v207 / v229 lessons): ReSTIR_Temporal_cs.hlsl and ReSTIR_Spatial_cs.hlsl both exist in TWO locations — `TestReSTIR_GI_Temporal_Data/` (the copy that actually compiles for the primary test) and `TestCornellBoxGI_Data/` (the control). Both copies must be edited in lock-step. Forgetting the Cornell copy would break the control's symbol-consistency check.
  2. **Cap value too aggressive** (256f): if a legitimate high-W reservoir actually has w_sum >> 256*targetLum (e.g., a very bright sample whose target is dim), the clamped W=256 may produce a darker indirect estimate than the unclamped version would have. ZetaRay uses 256 in production, so this is the principled value, but a tighter run (e.g., with strong fireflies) might prefer 64 or 1024. The plan defaults to 256; the plan-criticer may flag a different value.
  3. **Cap may hide the real cause** (instead of fixing it): the feedback loop is `w_sum_accum_next = w_sum_accum_curr + m_prev * targetLum_curr * W_prev`. Clamping W at store breaks the loop's multiplier, but the loop's additive accumulation of w_sum across frames is still unbounded. If `targetLum` is consistently small relative to the running w_sum, even with W clamped, w_sum will keep growing without bound. The plan therefore clamps W at store AND clamps `r.w_sum` to a parallel `k_MaxWSum` (e.g., 4096f — generous, well above any plausible w_sum accumulator). The line-528 `w_prev` already reads `r_prev[0].W` (the clamped value), so this composes safely.
  4. **Shader recompile time**: ~0.6s with slangc, so cheap. Acceptable.
  5. **The SuppressOutlierReservoirs guard** (line 558-563) already caps `r.M = 1.0f` when `r.w_sum > 25 * waveAvg`. With W also clamped, the firefly pattern the suppress-guard was designed for is suppressed at the source rather than at M; the guard can be left as-is (it's defensive and may still catch M outliers that don't manifest as W outliers).
