## Phase 1 — `VUID-vkCmdTraceRaysKHR-None-08608` spams every GI dispatch (FIXED)

### Symptom

Run from 2026-08-14 00:52 (`TestReSTIR_GI_Temporal.log`) — the test now
completes (exit 0) and the render window works, but every `vkCmdTraceRaysKHR`
from `FGIPass::DispatchRays` is flagged by the Vulkan Validation Layer:

```
error: [Vulkan] ERROR: Validation Error: [ VUID-vkCmdTraceRaysKHR-None-08608 ]
vkCmdTraceRaysKHR(): VkPipeline 0x84e20c0000000209[] doesn't set up
VK_DYNAMIC_STATE_VIEWPORT|VK_DYNAMIC_STATE_SCISSOR, but it calls the related
dynamic state setting commands.
```

The RT pipeline cannot be wrong (see root cause), so this is a validation
false positive — but it must be fixed, not ignored: it is an error-level
message repeated on every frame and it masks real validation output.

### Root cause

**Mechanism (verified against the installed VVL 1.3.280 sources):**

1. Every nvrhi graphics pipeline declares `VK_DYNAMIC_STATE_VIEWPORT` and
   `VK_DYNAMIC_STATE_SCISSOR` (`vulkan-graphics.cpp:384-386`), and
   `commitGraphicsState` records `vkCmdSetViewport`/`vkCmdSetScissor` on the
   command buffer whenever the viewport differs (`vulkan-graphics.cpp:570-591`).
   The GBuffer raster pass therefore records those commands every frame.
2. The validation layer tracks "dynamic state setting commands **since the
   last bound pipeline**" in a per-command-buffer mask
   (`dynamic_state_status.pipeline`). That mask is reset **only** when a
   **graphics** pipeline is bound (`PreCallRecordCmdBindPipeline`, graphics
   branch only). Binding a ray-tracing pipeline never resets it.
3. `vkCmdTraceRaysKHR` runs the same "doesn't set up … but it calls the
   related dynamic state setting commands" check against the RT pipeline.
   RT pipelines cannot declare `VK_DYNAMIC_STATE_VIEWPORT`/`SCISSOR`
   (`VUID-VkRayTracingPipelineCreateInfoKHR-pDynamicStates-03602`), so the
   stale VIEWPORT/SCISSOR bits from step 1 always trip
   `VUID-vkCmdTraceRaysKHR-None-08608` — even though **no** dynamic-state
   command was recorded after the RT pipeline bind. This is the well-known
   VVL 1.3.280 regression (see
   stackoverflow.com/questions/78339218 — "vkCmdTraceRays validation error
   with latest SDK"). Newer VVL versions fixed it by tracking only the RTX
   stack-size dynamic state at TraceRays (`ValidateTraceRaysDynamicStateSetStatus`).

**Why the in-tree "fix" (v167) was wrong:**

A previous attempt added, right before the RT bind:

```cpp
m_CurrentCmdBuf->cmdBuf.setViewport(0, 0, nullptr);
m_CurrentCmdBuf->cmdBuf.setScissor(0, 0, nullptr);
```

This does not work and is itself invalid:

- `vkCmdSetViewport` with `viewportCount == 0` violates
  `VUID-vkCmdSetViewport-viewportCount-arraylength` ("viewportCount must be
  greater than 0") — it would add a *new* validation error.
- The VVL state tracker's `RecordStateCmd` **ORs** the VIEWPORT/SCISSOR bits
  into the mask; a count-0 call still sets the same bits. The bits are only
  cleared by a graphics-pipeline bind, so the 08608 at TraceRays would have
  persisted.

### Changes

**nvrhi (`src/vulkan/vulkan-raytracing.cpp`, `setRayTracingState`):**

Replace the v167 count-0 "clear" with a v168 re-bind of the currently bound
graphics pipeline (if any) immediately before the RT pipeline bind:

```cpp
if (m_CurrentGraphicsState.pipeline)
{
    GraphicsPipeline* GfxPso = checked_cast<GraphicsPipeline*>(m_CurrentGraphicsState.pipeline);
    m_CurrentCmdBuf->cmdBuf.bindPipeline(vk::PipelineBindPoint::eGraphics, GfxPso->pipeline);
}
```

Why this is correct and safe:

- A graphics-pipeline bind is the only action that resets the VVL mask; the
  re-bind clears the stale VIEWPORT/SCISSOR bits before the RT bind.
- It is spec-legal: `vkCmdBindPipeline` outside a render pass executes
  nothing, and TraceRays is always outside a render pass.
- It does not disturb graphics state: the graphics pipeline declares
  viewport/scissor dynamic, so VVL keeps the values; nvrhi's own
  `m_CurrentGraphicsState` is untouched, so the next `setGraphicsState`
  behaves exactly as before.
- It is a no-op on newer VVL versions (which no longer run this check for
  RT pipelines).
